# SolarSight interview prep - 25 questions with answers

Answers are grounded in THIS project's real numbers and decisions. Learn the
facts, not just the phrasing: dataset 7,339 images / 8 classes; model
YOLO11-nano fine-tune; CPU run 10 epochs @ 320px; test split only 15 images;
conf threshold 0.40, IoU 0.45; Streamlit + Supabase; 33 tests.

## YOLO & the model

**1. What is YOLO, in one sentence?**
A single-pass object detector: one convolutional network looks at the whole
image once and directly outputs boxes + class probabilities, which is why
it's fast enough for interactive use (76 ms/image on my CPU for the nano
model).

**2. What does the model output before post-processing?**
For my yolo11n at 320px: a grid of anchor-free predictions with a class
score and box refinement per cell. Raw output has thousands of candidate
boxes with low scores; ultralytics then applies confidence filtering and
Non-Maximum Suppression before I ever see a `Results` object.

**3. Explain IoU.**
Intersection-over-Union: area of overlap divided by area of union between
two boxes. 1.0 = identical, 0 = no overlap. I use it two ways: NMS merging
(IoU threshold 0.45 - a box is considered a duplicate if it overlaps a
kept box more than that) and evaluation (a prediction "hits" a ground-truth
box at IoU >= 0.5 for mAP50).

**4. Explain NMS and why it matters here.**
Non-Maximum Suppression: sort boxes by confidence, keep the best, drop every
box that overlaps it above the IoU threshold, repeat. Without it, one hot
panel would produce 5-10 overlapping boxes. It runs inside ultralytics
during `model.predict`, driven by my sidebar IoU slider.

**5. What is mAP50 vs mAP50-95?**
Mean Average Precision across classes at IoU 0.5, and averaged over IoU
thresholds 0.5-0.95 in steps of 0.05. mAP50 asks "did you find it roughly
right"; mAP50-95 demands precise localisation. I report both in
docs/TRAINING.md, generated by training/evaluate.py - never typed by hand.

**6. Precision vs recall - which hurts an inspector more?**
Precision = of my alarms, how many are real. Recall = of real faults, how
many I catch. For solar inspection, missed faults (low recall) are worse:
a skipped hotspot can fail the string later. That said, an inspector
drowning in false alarms stops trusting the tool, which is why the default
confidence threshold is 0.40 and user-adjustable in the sidebar.

**7. Why YOLO11-nano and not s/m/l?**
No GPU locally, and nano fine-tunes fast while staying ~5 MB. For 640px
thermal imagery with 8 classes, the bigger variants would buy accuracy I
can't honestly train in this environment. The Colab notebook
(training/colab_train_gpu.ipynb) exists to train the bigger configuration
properly on a free T4.

**8. Walk me through what happens when I upload an image.**
Streamlit receives bytes -> PIL decodes to RGB -> `run_detection` sends BGR
to the cached YOLO model with conf=0.40, IoU=0.45 -> ultralytics runs
inference + NMS -> `results_to_detections` converts tensors to plain
`Detection` records -> confidence filter -> PIL draws boxes -> table renders
-> on click, `save_inspection` writes parent + children rows to Supabase.

## Dataset & training

**9. What dataset did you use and what's the licence?**
"Thermal Solar PV Anomaly Detection Dataset" (ThermoSolar-PV) on Kaggle
(pkdarabi/solarpanel), CC BY-NC 4.0 - attribution + non-commercial, which
is fine for this portfolio project. Provenance is a Roboflow project
(solarpanels-odahn/anomalies-detection-blv72 v14). I verified every number
in docs/DATA.md by reading the downloaded files, and download_data.py
re-verifies on every run.

**10. Why are the classes so imbalanced and how did you cope?**
Real-world fault frequencies leak into the labels: SingleHotSpot has 7,636
instances, StringReversedPolarity only 124 (61x). I coped by evaluating
per-class (weak classes are visible instead of hidden behind the mean),
keeping augmentation modest, and documenting that rare-class metrics are
unreliable. Weighted loss / oversampling is in the roadmap, not faked in
results.

**11. Your dataset has augmented near-duplicates - why does that matter?**
The authors created 3 augmented copies of every source image; near-
duplicates can land in both train and valid, so valid/test metrics are
optimistic versus genuinely unseen sites. The honest fix is a site-level
split - documented in docs/DATA.md limitations and the roadmap.

**12. Did you train on a GPU?**
No - this machine has no GPU (I checked with torch/nvidia-smi). I ran a
real reduced CPU fine-tune (yolo11n, 10 epochs, 320px, batch 8) to
validate the whole pipeline end to end, and I provide a Colab notebook for
the full 640px/60-epoch run. I can show the actual training log and the
metrics evaluate.py produced - I never claim a run I didn't do.

**13. How did you pick hyperparameters?**
Defaults close to ultralytics': lr0=0.01 SGD schedule, mosaic on, fliplr=0.5
but flipud=0 (drone footage has a natural "up"), patience=15 early
stopping, seed=42 for reproducibility. Epochs/imgsz/batch are CLI flags so
a run can be tuned without editing code, and every choice is recorded in
docs/TRAINING.md next to its measured result.

**14. What is overfitting and how would you detect it here?**
The model memorising training data instead of learning general features -
train loss keeps falling while validation mAP stalls or drops. I watch the
per-epoch validation metrics in the training log and the results.csv
ultralytics writes; patience-based early stopping halts before it gets
ugly. With augmented near-duplicates across splits (Q11), true
generalisation is best measured on unseen sites.

**15. Why is the dataset "only" 7,339 images and is that enough?**
Thermal drone inspection is niche: imagery is expensive to collect and
labelling needs domain experts. 7.3k with ~21k boxes is workable for
fine-tuning a pretrained detector (transfer learning carries most of the
weight) but small for from-scratch training. The 15-image test split is a
real weakness I mitigate by also reporting the 400-image valid split.

## App, DB, testing, delivery

**16. Why Streamlit instead of React + FastAPI?**
Scope: the goal is a working inspector tool, not a product. Streamlit gives
upload, interactive sliders, charts and tables in ~300 lines of Python.
Trade-offs I can name: full page re-runs per interaction, one process, no
real multi-user concurrency. If this became a product, I'd extract the
pipelines package as-is (it's already framework-free) behind a FastAPI
service.

**17. Why store metadata only, not images?**
Keeps the DB small, avoids blob storage costs, and there's no personal data
in a thermal panel photo. Trade-off: History can't re-display the original
media - only what was found. Adding Supabase Storage thumbnails is roadmap
item #2.

**18. Walk me through the SQL schema.**
`inspections`: uuid PK, site_name, source_filename, media_type
(image/video check), model_version, created_at, total_faults.
`detections`: uuid PK, FK to inspections with ON DELETE CASCADE, class_name,
confidence (0-1 check), box corners as double precision, nullable track_id
(null for images). Three indexes: created_at desc for the history listing,
inspection_id for drill-down, class_name for aggregation. RLS enabled with
anon INSERT/SELECT-only policies (no UPDATE/DELETE) because this demo has no auth.

**19. How do you test ML code without a GPU or even the model?**
Seams. Ultralytics is imported in exactly one function, so tests never
import torch. `results_to_detections` duck-types its input, so tests feed
`FakeBoxes`/`FakeResult` objects with torch-like `.cpu().numpy()`. The DB
class takes its client via constructor injection, so tests use an
in-memory fake implementing the same fluent API. Result: 33 tests in 2.5s
covering conversion, filtering, empty cases, dedupe, row mapping,
aggregation, CSV round-trip, drawing, plus AppTest boot tests.

**20. What do your tests NOT cover?**
Real model accuracy (that's evaluate.py's job on the real test split),
ByteTrack behaviour across frames (needs the real tracker), actual network
I/O to Supabase (fakes don't validate RLS or network errors), and Docker
runtime (covered by building the image and hitting the health endpoint
manually). Being able to say this crisply is part of the point.

**21. How does video deduplication work?**
`model.track(persist=True)` runs ByteTrack: it matches detections between
consecutive frames by IoU + appearance, assigning a stable track_id per
panel. Per frame I get detections; `dedupe_by_track` keeps each track's
highest-confidence appearance, so a panel tracked through 200 frames is
one record, not 200. Without `persist=True` the tracker resets every call
and dedup would silently break - that's the bug the tests would catch.

**22. Why Docker, and what's the HEALTHCHECK do?**
Reproducible deployment: the image pins Python 3.11-slim and the exact
dependency set; CPU-only torch keeps it ~1 GB instead of ~3 GB with CUDA
wheels. HEALTHCHECK curls `/_stcore/health` so orchestrators know when the
server is actually up (start-period 40s covers model import time).
Secrets and weights are mounted, never baked into the image.

**23. What does CI do, and why install CPU torch first?**
GitHub Actions: checkout, Python 3.11 with pip cache, CPU torch from the
PyTorch index, then requirements.txt, then `pytest -v`, then an import
check proving app.py loads with NO secrets present. CPU-first matters
because letting ultralytics resolve torch pulls the ~2 GB CUDA build,
wasting minutes on a runner with no GPU.

**24. Why Supabase over raw Postgres or Firebase?**
Supabase = hosted Postgres + instant REST (PostgREST) + a Python client,
so I write no API layer and still keep a real relational schema with FKs,
checks and indexes. The anon key + RLS keeps the demo safe-enough without
building auth. Firebase would push me toward NoSQL shapes that fit the
per-inspection drill-down worse.

**25. A fault's confidence is 0.41 - explain exactly what that number is.**
It's the model's softmax score for the class of the best candidate box
surviving NMS - "the network's posterior-ish belief this region is this
class", not a probability of being a true fault in the calibration sense.
Above my 0.40 threshold by a hair: it's shown, stored, and flagged as
weak in interpretation. The threshold is a product decision, which is why
it's a slider, not a constant buried in code.

## Honest limitations & what I'd improve next

1. Trained with a reduced CPU run; the full-quality model needs the Colab
   GPU notebook (documented, not hidden).
2. Test split is 15 images / 31 boxes; 3 of 8 classes absent from it.
   Per-class test numbers are noisy - I lean on valid (400 images) too.
3. Near-duplicate augmented images across splits inflate metrics; a
   site-level split would measure real generalisation.
4. Severe class imbalance unaddressed beyond evaluation transparency;
   weighted sampling is next.
5. No auth; the anon key can insert and read every row (it cannot update or delete).
   Fine for a demo, not production: a real app would scope policies to `auth.uid()`.
6. No image/thumbnail persistence; History can't re-display media.
7. No temperature calibration (grayscale intensity only).
8. Streamlit single-process model: no concurrent multi-user writes at scale.

Say these proactively in an interview - "here's what's weak and here's the
next step" reads far better than being caught out.
